# 第一模块：全栈工程架构视角（Full-Stack Architecture）

从现代全栈工程的角度看，Pi Native CRM 解决的是企业中最核心的业务三要素：**客户（Who）、商机与流程（What）、全渠道沟通（How）**。系统采用前后端一体化的现代技术栈，但内部有着极其严密的信任分界与状态分工。

## 1.1 前后端分工与运行时拓扑

整个全栈系统自上而下分为四层物理与逻辑边界：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        1. 浏览器与呈现层 (Client UI)                   │

└───────────────────────────────────┬────────────────────────────────────┘

┌───────────────────────────────────▼────────────────────────────────────┐
│                  2. 边缘网关与服务端层 (Server & API)                  │
```

## 1.2 全栈架构的关键构造要点

1. **前后端同构，但信任边界绝对隔离：**
   Next.js 16 使得页面代码与 API 路由位于同一个仓库。但同仓库不等于共享信任。浏览器永远只持有展示状态（通过 TanStack Query 维护数据副本）；所有的业务规则校验、权限守卫（RBAC）与审计记录，全部发生在服务端的 Route Handlers 中。
2. **多租户安全下沉至数据库引擎（RLS by-design）：**
   系统服务于多个企业租户。如果把多租户数据隔离寄托于工程师在业务代码里写 `where organization_id = ...`，越权漏洞迟早会发生。本系统在所有业务表上强制开启 Postgres **行级安全（Row Level Security, RLS）**，通过底层的 `fn_user_org_ids()` 策略，跨租户数据在 SQL 查询级别直接“物理隐形”。
3. **核心事务与外部副作用彻底解耦（Event Sourcing 设计）：**
   这是保证系统高可靠性的核心设计：**Postgres 数据库触发器永不发起外部 HTTP 请求！** 当业务状态变更时，触发器仅向 `event_log` 写入一条轻量事件记录。发信、调用模型、索引 RAG、语音呼叫等所有高延迟或可能失败的外部副作用，全部由后台独立 Worker 轮询消费。即使 WhatsApp 网关或大模型接口暂时超时，核心 CRM 事务也不会被挂起或回滚。
4. **全渠道网关接入（Ingress）：**
   外部世界通过标准 Webhook 接入系统。WhatsApp 消息经由 WAHA (WhatsApp HTTP API, NOWEB 引擎) 验签后送入系统；语音呼叫通过 Asterisk SIP 交换机接入；外部开发者通过 MCP (Model Context Protocol) 协议将 CRM 作为工具调用。

# 第二模块：Agent 智能体架构与 Pi SDK 深度剖析（The Agent Architecture）

这是本项目最核心的创新点：**它不是一个普通的 CRM 挂了一个 AI 聊天窗口，而是一个将 Agent 视为“一等公民（First-Class Citizen）”的 AI Native 业务工作台。**

## 2.1 认识本质：从“无状态模型”到“有状态智能体”

在理解代码之前，必须先理清关于 Agent 的本质知识：

| 对比维度 | 普通 LLM 模型调用 (Chat) | Pi Agent 智能体系统 (Agent) |
|---|---|---|
| **本质属性** | 无状态的“文本生成函数”（输入 Prompt，输出 Token） | 有状态的“自主环境交互系统”（拥有目标、状态机与工具集） |
| **交互模式** | 单轮或被动的请求-响应 | 自主的“思考-行动-观察（ReAct）”闭环指令循环 |
| **物理世界影响** | 仅能返回建议文本，无法感知或改变现实 | 通过受控工具读取数据库、调用外部接口、提出业务提案 |
| **错误恢复** | 报错即中断 | 能够读取工具报错信息，自主修正参数并再次尝试 |

## 2.2 Pi Agent Core SDK 的底层机制：智能体的指令周期（The Agent Loop）

系统底层深度集成了 `@earendil-works/pi-agent-core`。Pi SDK 为系统提供的是一个**严密的智能体运行时内核（Runtime Kernel）**。它在后台驱动的执行循环（Agent Loop）类似于操作系统的 CPU 指令周期：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Pi Agent Loop 指令周期循环                      │
│                                                                        │
│   ┌──────────────┐     1. 组装输入      ┌───────────────────┐          │
│   │ CRM 事实底座  │ ─────────────────> │   System Prompt   │          │
│   │ & 客户上下文 │                    │   + 历史消息池    │          │
│   └──────────────┘                    └─────────┬─────────┘          │
│                                                 │ 2. 流式调用        │
│                                                 ▼                    │
│                                       ┌───────────────────┐          │
│                                       │   大语言模型 (LLM) │          │
│                                       └─────────┬─────────┘          │
│                                                 │                    │
│                        ┌────────────────────────┴──────────────┐     │
│                        ▼ 3a. 输出文本                          ▼ 3b. │
│              ┌───────────────────┐                   ┌──────────────┐│
│              │   产生最终交付    │                   │ 发起工具调用 ││
│              │ submit_workbench_ │                   │  Tool Calls  ││
│              │      result       │                   └──────┬───────┘│
│              └─────────┬─────────┘                          │ 4. 拦截│
│                        │                                    ▼ & 执行 │
│                        │                             ┌──────────────┐│
│                        │                             │ CRM 受控工具 ││
│                        │                             │ (只读/提案)  ││
│                        │                             └──────┬───────┘│
│                        │                                    │ 5. 回灌│
│                        │      6. 结果作为新的环境观察       │ 观察   │
│                        │ <──────────────────────────────────┘ 事实   │
│                        ▼                                             │
│                [ 循环评估结束 ]                                      │
└────────────────────────────────────────────────────────────────────────┘
```

**Pi 循环的五个核心生命周期：**

1. **上下文投影（Context Projection）：** 进入循环前，CRM 会把当前客户事实、组织政策、历史会话与当前商机动态装配为第一条带有时间戳的 Context。
2. **模型流式推理（Model Stream）：** 通过 Model Gateway 适配不同 Provider（Anthropic / OpenAI / DeepSeek），模型一边流式生成思考，一边决定是否调用工具。
3. **工具拦截与守卫（beforeToolCall）：** 这是 Pi 提供的关键安全挂钩。在工具代码真正运行前，CRM 护栏会检查入参合法性、权限范围与预算额度。若发现越权，可在此刻直接阻断。
4. **执行与观察回灌（Tool Observation）：** 工具执行完毕后，返回值包装为标准格式写回上下文。模型在下一轮看到的不再是它自己的猜测，而是**真实的系统事实（Observation）**。如果工具执行报错，模型会阅读错误原因并在下一轮自主重试。
5. **终止判定与结构化交付（Termination & Submission）：** 循环不能无限进行。系统设有轮次上限（Max Turns）与 Token 预算门禁。当 Agent 完成任务时，必须通过受控的提交口 `submit_workbench_result` 交付结构化摘要与事实依据，而不是随意输出散漫文字。

## 2.3 Agent 工程的关键认知与设计哲学

在 Pi SDK 之上，系统贯彻了五项顶尖的智能体工程设计规范：

### 要点一：工具安全四级分类与“可逆写”设计
系统严禁将裸 SQL 或未经保护的修改接口直接暴露给 Agent。所有工具分为严格的四级：
- **Read（只读工具）：** 如查询客户档案、检索会话记录。无外部副作用，Agent 循环内直接调用。
- **Reversible Write（可逆写入）：** 如更新商机标题或阶段。必须具备前置快照（Snapshot）与 `expected_updated_at` 乐观锁。系统保存回滚补偿参数，防止并发冲突覆盖他人修改。
- **External（外部动作）：** 如向客户发送 WhatsApp 消息、预订外部日程。这是不可逆操作，**Agent 绝对无法直接调用生效**。
- **Irreversible（高危操作）：** 删除数据、签署协议等，强制阻断。

### 要点二：人机协同（HITL, Human-in-the-Loop）与提案状态机
**为什么起草回复不等于发送客户？** 这是防范大模型幻觉灾难的核心哲学：
在 Agent 工作台中，模型生成的回复建议只是**内存中的推理草稿**。当 Agent 认为需要推进业务时，系统会生成一张 `Action Proposal`（行动提案），并将运行状态机置为 `awaiting_confirmation` 挂起等待。只有当销售员在 UI 上核验无误并点击批准后，系统才通过两阶段事务正式调用渠道外发。**把决策权留给人类，把繁重的信息检索与草案整理交给 Agent。**

### 要点三：三级记忆体系（事实 vs 偏好 vs 政策）
智能体不是把所有资料胡乱塞进 Prompt，而是建立了严密的“三级记忆分工”：
1. **SQL 强一致事实（Postgres）：** 客户电话、商机金额、历史跟进时间。这是唯一真理（SOT），绝不容许模型自由发挥。
2. **动态个性化偏好（Mem0）：** 如“林女士倾向于看文字方案而非电话沟通”、“客户对交付周期非常敏感”。这类信息通过动态加权与更新，帮助 Agent 调整沟通风格。
3. **非结构化组织知识（RAG / pgvector）：** 产品说明书、售后退换政策。通过语义检索召回，Agent 输出结论时必须附带知识库版本引用，证据不足时必须诚实声明“资料缺失”。

### 要点四：模型网关（Model Gateway）与 BYOK 治理
系统为每个企业租户提供自带模型密钥（Bring Your Own Key, BYOK）能力。凭证在数据库中对称加密存储，仅在发起模型调用时瞬时解密。网关负责：多模型适配、月度费用与 Token 预算预检、计费日志审计（Audit Log），从物理层面上杜绝因 Agent 递归死循环造成的巨额账单风险。

## 2.4 三大智能体生态集成：Mem0 记忆、腾讯 WeKnora 知识库与 Langfuse/LangChain 观测体系

在 Pi Agent Core 的基础循环之上，系统通过标准化的集成适配器（Integrations Adapter），深度接入了三个业界顶尖的专用智能体生态系统，分别解决了智能体的**“长效记忆”**、**“权威知识”**与**“生产可观测性”**三大难题：

### 1. Mem0：解决“跨会话长期失忆”的个性化客户记忆网络
- **业务痛点：** 大模型的上下文窗口再大，一次会话关闭后就彻底遗忘。但真实销售业务跨度长达数月，客户的沟通偏好（如“习惯看书面报价而非电话推销”、“对交期极度敏感”）无法沉淀。
- **系统接入与设计要点：**
  - **双轨制记忆分工：** 系统严守“Postgres 保存客观强事实（SOT，如订单金额、客户电话），Mem0 保存语义偏好与动态加权上下文”。两者绝不混淆。
  - **租户与隐私哈希隔离：** 为防止客户 PII 泄漏，系统向 Mem0 写入记忆时，并不传递原始用户 ID，而是以 `sha256("crm-customer:v1:" + orgId + ":" + contactId)` 作为隔离 Scope，确保跨租户绝对安全。
  - **两阶段确认状态机：** Agent 提取出的客户偏好，先在 Postgres 标记为 `in_flight`，经核验后才转为 `confirmed`。客户下一次进线时，Agent 会在上下文装配阶段动态拉取 Mem0 记忆，实现“越聊越懂客户”的长效体验。

### 2. 腾讯 WeKnora：解决“政策断章取义与知识幻觉”的企业级 LLM Wiki
- **业务痛点：** 普通向量检索（Naive RAG）常常将长文档切得支离破碎，导致 Agent 丢失上下文、引用过时政策，甚至胡乱编造报价。
- **系统接入与设计要点：**
  - **为什么引入腾讯 WeKnora：** WeKnora 是腾讯微信团队开源的企业级智能知识库与 Wiki 派生系统。它不仅能深度解析复杂文档，还能将原始文档派生为结构严谨、具备强关联的组织 Wiki 页面。
  - **带 64 位版本哈希的证据闭环：** Agent 通过 `searchCompanyWiki` 检索时，获得的每条证据都严格绑定 64 位版本哈希与原文 Chunk 引用。Agent 输出方案时必须附带 Wiki 证据链接；若来源文档已被管理员撤回或过期，系统立即阻断引用。
  - **诚实缺口报告（Evidence Gap）：** 若 WeKnora 中未命中已发布的权威页面，接口返回 `status: "unavailable"`，强制 Agent 如实回复“当前缺少相关产品政策依据”，彻底封死大模型伪造商业承诺的风险。

### 3. Langfuse & LangChain 生态：解决“黑盒黑产”的生产级 Trace 与自动化 Eval
- **业务痛点：** Agent 是由多轮“模型推理-工具调用”组成的复合链路。一旦线上出现慢请求、死循环或错误回答，如果缺乏全链路监控，工程师无从排查。
- **系统接入与设计要点：**
  - **全链路异步 Tracing：** 系统在 Pi Agent Core 运行时内置了 `RuntimeObservation` 旁路监听。模型流式耗时、每次 Tool 执行参数与结果、Token 吞吐量均被结构化捕获，通过轻量事件异步投递至 Langfuse，对 CRM 业务主请求做到 0 毫秒延迟损耗。
  - **PII 脱敏合规：** 在将 Trace 数据上报给 Langfuse 之前，系统通过正则与脱敏守卫清洗掉电话、银行账户等敏感隐私，只保留结构化执行轨迹与状态元数据。
  - **自动化评测（Eval & Judge）：** 系统结合 LangChain 生态与标准评测契约，建立双重门禁：**确定性断言（如工具调用成功率、敏感词拦截）** + **LLM-as-a-Judge（大模型裁判员语义打分）**，为每一次 Agent 执行给出量化评分，驱动 Prompt 与工具链的持续演进。

# 总结：如何向他人介绍这个项目？

当新成员或业务方问起这个项目时，可以用这三句话清晰总结：

1. **在全栈层面：** 它是一个基于 Next.js 16 和 Supabase Postgres 的自托管企业级 CRM，依靠 RLS 实现数据库层级的租户安全防线，依靠轻量级事件总线解耦前后端事务与外部通信。
2. **在智能体层面：** 它以 Pi Agent Core 为运行时核心，把模型封装进严密的“思考-工具-观察”闭环，实现了专职 Agent 协同与结构化交付。
3. **在人机协作层面：** 它牢牢守住“CRM 拥有事实、Agent 拥有推理、人类拥有最终决策”的安全铁律，通过行动提案（Proposal）与审批机制，让大模型在可控、可信、可解释的缰绳下服务于真实业务。
