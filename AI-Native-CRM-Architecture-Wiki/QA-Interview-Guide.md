# 第一模块：项目宏观定位与全栈架构篇

### Q1: 请用 1~2 分钟介绍一下这个 AI Native CRM 项目？
- **【考察意图】** 考察技术全局观、业务抽象能力与“电梯演讲”表达力。
- **【高分回答策略】**
  > 我主导/参与的这个项目是一个**自托管、多租户、原生集成智能体（AI Native）的企业级客户关系管理系统**。
  > 
  > 传统的 CRM 本质上是“人记录、人流转”的静态数据库；而我们系统的核心突破在于：**将 AI Agent 作为系统的一等公民（First-Class Citizen）**，构建了完整的“客户 360 事实感知 → 智能体自主推理建议 → 行动提案人工审批（HITL） → 外部渠道受控外发”的业务闭环。
  > 
  > 在技术架构上分为两大支柱：
  > 1. **全栈工程基座**：基于 Next.js 16 App Router 前后端同构架构，数据层采用 Supabase Postgres，利用数据库原生的 **RLS（行级安全策略）** 实现物理级的租户硬隔离，并通过轻量级事件总线（`event_log`）实现核心事务与外部副作用彻底解耦；
  > 2. **智能体大脑**：深度集成 **Pi Agent Core SDK**，构建了严格受控的 Agent Loop 指令周期；同时接入 **Mem0（长效偏好记忆）**、**腾讯 WeKnora（企业级 LLM Wiki 知识图谱）** 以及 **Langfuse（异步 Tracing 与语义 Eval 门禁）**，形成了一套具备企业级安全约束的智能化解决方案。

### Q2: 为什么选用 Next.js 16 + Supabase Postgres？前后端如何划分信任边界？
- **【考察意图】** 考察全栈技术选型的思考深度，以及对前后端同构代码中安全信任边界的把握。
- **【高分回答策略】**
  > 选型 Next.js 16 App Router 的核心原因是**全栈效能与类型同构**。页面渲染与 160 多个 RESTful API Route Handlers 在同一代码库，使前端与后端可以强共享 TypeScript 类型契约（如 Zod Schema），大幅降低协同开销。
  > 
  > 但**同仓库绝不等于同信任**，我们在架构上做了极其严格的分界：
  > 1. **浏览器永远只持有展示状态**：前端通过 React 19 Client Components 管理 UI 局部状态，通过 TanStack Query 维护服务端数据的只读缓存副本，前端无权执行特权决策；
  > 2. **边缘网关初步校验**：所有流量首先经过 `proxy.ts` 边缘代理，注入全局唯一的 `X-Request-Id` 用于链路追踪，并分流公开路由与会话有效性；
  > 3. **服务端 Route Handlers 统一守卫**：支持前端 Cookie（`sb-pi-native-auth`）与外部服务间 Bearer Token 双重鉴权；强制调用 `resolveActiveOrg()` 从已签名的 JWT 凭证中解析租户身份，**严禁信任请求 Body 传入的组织 ID**；所有入参由 Zod 强校验后才允许进入业务逻辑。

### Q3: 系统的多租户隔离（Multi-tenancy）是如何从数据库底层防范越权的？
- **【考察意图】** 考察高并发 SaaS / 自托管系统的多租户安全设计，防范越权漏洞的深度思考。
- **【高分回答策略】**
  > 很多初级系统的多租户隔离是依靠工程师在业务代码里手写 `where organization_id = ...`，这种方案在团队协作和复杂关联查询中极易出现越权漏洞。
  > 
  > 在我们项目中，贯彻的是 **Multi-tenancy by-design**，将隔离防护**下沉到了数据库引擎层**：
  > 1. 所有带租户属性的业务表均包含 `organization_id uuid not null` 外键；
  > 2. 数据库层面全量开启 Postgres 的 **RLS（Row Level Security，行级安全策略）**；
  > 3. RLS 策略强制绑定安全辅助函数 `fn_user_org_ids()`，只有当前会话经过 Supabase Auth 验证并拥有该组织成员身份时，数据库才会返回对应的数据行。跨租户数据在 SQL 执行层直接“物理隐形”；
  > 4. 即使在少数必须使用 `service_role`（绕过 RLS）的后台管理场景中，代码规范也强制要求从可信会话中解析组织上下文手动追加过滤，杜绝任何参数篡改攻击。

### Q4: 为什么架构要求“数据库触发器绝不发起 HTTP”？异步事件总线如何设计？
- **【考察意图】** 考察高可靠分布式系统设计、事务边界划分及 Event Sourcing 理解。
- **【高分回答策略】**
  > 这是一条核心架构红线：**Postgres 触发器绝对禁止发起外部网络/HTTP 调用！**
  > 
  > 原因在于外部 HTTP 调用（调大模型 API、发 WhatsApp 消息）存在网络波动、延迟高、不可控的特点。如果放在数据库事务或触发器内，一旦网络抖动或第三方超时，数据库连接就会被长时间占用，导致数据库连接池耗尽、锁竞争激增，甚至引发主库雪崩。
  > 
  > 我们的解法是**轻量级 Event Sourcing（事件溯源）架构**：
  > 1. 业务发生变更时，数据库触发器或业务写操作仅向内部的 `event_log` 表插入一条不可篡改的事件日志，核心主事务毫秒级提交；
  > 2. 外部副作用（AI 响应、RAG 向量索引、WhatsApp 消息发送、脱敏清洗）交由后台 10 个独立的 Cron/Worker 端点异步拉取消费；
  > 3. 通过 `unique(organization_id, external_id)` 保证消费幂等性。即便大模型接口挂掉或限流，系统只需记录退避重试或死信告警，核心 CRM 业务完全不受影响。

### Q5: 外部全渠道（WhatsApp、SIP 语音）是如何接入系统的？
- **【考察意图】** 考察真实外部通信系统对接、协议适配与防封控工程实践。
- **【高分回答策略】**
  > 系统设计了统一的通信通道接入层（Ingress）：
  > 1. **WhatsApp 通道**：基于 **WAHA Plus（NOWEB 引擎）** 搭建独立网关。入站消息通过 HMAC-SHA512 签名防伪验证后接入 Webhook；底层封装了针对 Meta 官方风控的节流（Throttle）算法与 STOP 拒收退订拦截器；
  > 2. **语音电话通道**：采用 Asterisk SIP 交换机，支持双通路事件桥接。通话录音流异步转存至私有对象存储，并严格遵循合规留存用户通话知情同意记录；
  > 3. 所有入站消息在网关层标准化后，统一进入 `event_log` 事件管道，驱动收件箱（Inbox）实时刷新及后续 Agent 自动唤醒。

# 第二模块：Agent 智能体核心机制与 Pi SDK 深度篇

### Q6: 它与市面上普通的“套壳 AI 聊天”有何本质区别？
- **【考察意图】** 考察对大模型（LLM）与自主智能体（Agent）概念边界的深度理解。
- **【高分回答策略】**
  > 市面上常见的套壳产品，本质是**无状态的文本生成管道**（输入聊天记录，模型吐出一段文字），模型既不能感知真实系统状态，也无法对真实世界产生副作用。
  > 
  > 而我们的系统是将 Agent 作为**有状态的自主业务系统**：
  > 1. **事实权威在 CRM，推理能力在模型**：Agent 绝不拥有任意写数据库的特权。它的所有输入来自 CRM 的结构化投影，所有推论必须给出证据引用（Grounding）；
  > 2. **具备闭环指令周期（Agent Loop）**：基于 Pi Agent Core，模型能够自主进行‘理解任务 → 选择工具 → 执行查询 → 观察环境结果 → 纠偏自愈 → 结构化交付’的多轮循环；
  > 3. **具备人机协同的受控执行机制**：Agent 提出的业务变更，不是直接写库，而是生成带状态机的 Action Proposal，经由人类确认后走双事务落地。

### Q7: 为什么基于 Pi Agent Core SDK 构建？智能体的指令周期（Agent Loop）是如何运转的？
- **【考察意图】** 考察对智能体底层执行内核、循环状态机与框架选型的深度认知。
- **【高分回答策略】**
  > 我们基于专门的 **Pi Agent Core SDK（`@earendil-works/pi-agent-core`）** 作为底层运行时内核。它的核心优势是极简、高性能，将 Agent 抽象为类似于**操作系统 CPU 指令周期**的严密执行回路：
  > 
  > 整个 **Pi Agent Loop** 分为五个标准阶段：
  > 1. **输入与上下文组装**：CRM 将租户策略、带时间戳的客户事实、历史记录组装为结构化 Prompt 注入 Pi；
  > 2. **模型流式推理（Stream）**：调用 Model Gateway 流式解析，模型一边输出思考链，一边判断是否发起受控工具调用（Tool Calls）；
  > 3. **工具前置拦截（`beforeToolCall`）**：在工具真正执行前触发安全守卫，校验参数模式、权限范围及 Token 预算；若发现违规可原地阻断；
  > 4. **工具执行与观察回灌（Tool Observation）**：执行工具后，将真实的客观结果包装为 Observation 回灌给模型。如果报错，模型在下一轮循环中会自主阅读错误并重试修复；
  > 5. **终止判定与交付**：设置最大轮次（Max Turns）与预算熔断保护。Agent 达成目标后，必须调用专属的交付接口 `submit_workbench_result` 提交结构化摘要与证据列表，正式结束循环。

### Q8: Agent 的受控工具有哪些安全分级？什么是带有乐观锁的“可逆写”？
- **【考察意图】** 考察生产级智能体系统的安全性设计、工具防御分层与事务并发控制。
- **【高分回答策略】**
  > 为了彻底防范大模型越权或误操作破坏生产数据，我们对 Agent 暴露的工具进行了严格的**四级效果分级（Tool Effect Classification）**：
  > 1. **Read（只读工具）**：如查询客户资料、搜索历史聊天。无副作用，Agent 可以在循环内随时自由调用；
  > 2. **Reversible Write（可逆写入）**：如修改商机标题或阶段。必须具备**前置状态快照（Snapshot）**与 **`expected_updated_at` 乐观并发锁**，同时系统自动登记逆向补偿参数。若发生并发修改，系统通过乐观锁自动发现冲突并安全回滚；
  > 3. **External（外部动作）**：如向客户发送 WhatsApp 消息、预定外部会议。此类操作具有不可逆的现实影响，**Agent 绝对禁止私自直接生效**，必须降级为提案（Proposal）；
  > 4. **Irreversible（高危破坏操作）**：如物理删除客户、清空数据表。系统在工具清单层直接禁止暴露给模型。

### Q9: 什么是 HITL（人机协同）？为什么系统坚持“起草回复不等于外部发送”？
- **【考察意图】** 考察大模型防幻觉灾难、企业级合规控制与 HITL 状态机落地能力。
- **【高分回答策略】**
  > 很多初学者会有一个误区，认为 Agent 生成了回复就应该自动发给客户。但在严肃商业场景中，大模型的幻觉一旦未经审核直接外发，可能给企业带来毁灭性的信誉或法律灾难。
  > 
  > 因此我们贯彻了核心哲学：**区分‘推理起草’与‘副作用执行’**。
  > 1. 在智能体工作台中，模型生成的沟通建议、方案摘要，在架构上纯属**内存中的思考草案**；
  > 2. 当 Agent 认为应该推进业务时，系统会生成一张带有确定性参数的 `Action Proposal`（行动提案），并将该任务单挂起为 `awaiting_confirmation` 状态；
  > 3. 人类销售人员在 UI 上核对提案内容，一键点击批准；
  > 4. 系统通过**‘领取事务（行锁抢占） → 执行工具调用 → 结算事务（落账与状态翻转）’**的双事务机制完成真实发送。**人类牢牢掌握最终决策权，大模型负责繁重的分析与拟稿**。

### Q10: 面对复杂的客户业务，系统内的多 Agent 是如何分工协作的？
- **【考察意图】** 考察多智能体（Multi-Agent）编排机制、专职角色（Specialist）分工设计。
- **【高分回答策略】**
  > 系统设计了四个具有明确权责契约的内置专职 Agent（Builtin Agents）：
  > 1. **CRM 情报员（`crm_intelligence`）**：专职只读分析。负责交叉核对客户 360 数据、聊天历史、时间线，提取客户异议并标记‘事实、推论与未知’；
  > 2. **销售运营专员（`sales_operations`）**：聚焦漏斗与商机推进。评估商机推进条件，生成阶段变更的 Reversible Write 提案；
  > 3. **客户沟通专员（`customer_communications`）**：聚焦沟通方案拟定。结合客户历史偏好生成个性化回复草稿，并构建 External 发送提案；
  > 4. **CRM 监督员（`crm_supervisor`）**：充当质量审查与合规哨兵。审核其他专员的推论是否具备证据支撑，检查是否越权或违背组织政策。
  > 各专职 Agent 各司其职，避免了单一模型 Prompt 过于冗长造成的注意力涣散与混乱。

# 第三模块：三大外部生态（Mem0 / 腾讯 WeKnora / Langfuse）篇

### Q11: 系统的记忆网络是如何设计的？Mem0 与 Postgres SQL 事实如何分工？
- **【考察意图】** 考察记忆体系分层设计（短期/长期/事实/偏好）以及 Mem0 的工程整合深度。
- **【高分回答策略】**
  > 我们构建了清晰的**‘三级记忆金字塔’**，坚决不把所有数据混为一谈：
  > 1. **第一级：Postgres SQL 强事实（SOT 唯一真理）**：存储电话、成交金额、跟进日程、订单状态等硬核业务记录。特点是强一致性、带唯一约束与外键，绝不容许大模型模糊发挥；
  > 2. **第二级：Mem0 个性化长效偏好记忆**：存储客户的自然语言特征（如：沟通偏好、行业特殊术语、对价格/交期的敏感度）。特点是支持跨会话长期沉淀、动态加权衰减与语义召回；
  > 3. **第三级：pgvector / WeKnora 组织政策与知识**：存储公司标准产品手册、服务退换政策。特点是语义切片检索，要求严格带版本溯源。

### Q12: 接入外部 Mem0 时，如何防范多租户越权与客户隐私（PII）泄露？
- **【考察意图】** 考察企业级合规性（LGPD/GDPR）实施细节，以及对第三方外部服务接入的安全防卫。
- **【高分回答策略】**
  > 在与 Mem0 的实际集成（`lib/ai/integrations/mem0.ts`）中，我们设计了两大关键安全防线：
  > 1. **SHA-256 租户哈希隔离 Scope**：系统向 Mem0 写入和查询记忆时，**绝对不传输真实的客户 ID、手机号或姓名明文**，而是使用包含组织前缀的哈希标识 `sha256("crm-customer:v1:" + orgId + ":" + contactId)`。每个租户在 Mem0 的向量空间中物理隔离，哪怕外部服务数据泄漏，也完全无法反解出任何真实业务实体；
  > 2. **两阶段防污染状态机**：模型提取出的客户偏好，首先在本地数据库写入并标记为 `in_flight`；只有经由人工核验或高置信度验证后，才正式标记为 `confirmed`，有效防止模型把单次对话的偶然调侃误当成永久记忆。

### Q13: 企业知识库为何接入腾讯 WeKnora？它如何根治普通 RAG 的“断章取义与幻觉”？
- **【考察意图】** 考察高阶 RAG 架构设计、企业级文档管理以及防范过时政策知识幻觉的方案。
- **【高分回答策略】**
  > 传统 Naive RAG 只做简单的向量切片，容易出现两个致命伤：切片丢失上下文约束（断章取义），以及制度更新后仍检索到已作废的旧政策（版本失效）。
  > 
  > 我们接入腾讯微信团队开源的 **WeKnora**（`agent-services-weknora-v0.8.2`）作为企业级 LLM Wiki 引擎：
  > 1. **文档深度解析与派生 Wiki**：WeKnora 能将复杂的业务手册解析并派生为具备语义关联的结构化 Wiki 页面，保留完整的政策上下文边界；
  > 2. **64 位版本哈希证据溯源（Evidence Hash）**：Agent 检索到的每一条知识依据，都携带 64 位十六进制版本哈希与原文切片锚点。Agent 给出报价或政策建议时，必须附带此证据凭据；
  > 3. **诚实缺口回退（Evidence Gap）**：若 WeKnora 中对应的原始文档已被管理员更新或撤回，系统明确返回 `status: "unavailable"`，**强制 Agent 诚实承认‘当前缺少相关有效依据’**，从根源上杜绝大模型随意捏造企业商业承诺。

### Q14: 生产环境下如何监控黑盒 Agent？Langfuse 与语义评测（Eval）如何落地？
- **【考察意图】** 考察 LLMOps 生产级运维、链路追踪（Tracing）与智能体质量自动化评估闭环。
- **【高分回答策略】**
  > 针对生产环境中 Agent 调用链路长、排查难的问题，我们落地了 **Langfuse 异步观测与双重 Eval 质检体系**：
  > 1. **全链路异步非阻塞 Tracing**：在 Pi Agent Core 适配层中内置轻量观察者模式，流式推理耗时、每次 Tool 调用的参数、返回结果及 Token 吞吐均封装为 `RuntimeObservation`，通过异步队列发送给 Langfuse，对 CRM 用户端请求**实现 0 毫秒延迟损耗**；
  > 2. **PII 脱敏机制**：上报 Trace 前，脱敏守卫通过模式匹配清洗掉手机、邮箱等客户敏感数据，仅保留 `crm_run`, `crm_org` 等结构化元数据；
  > 3. **双重 Eval 门禁闭环**：结合 LangChain 生态标准，建立确定性断言（校验工具执行状态、参数契约） + **LLM-as-a-Judge（大模型裁判员）** 语义审查，对 Agent 交付的最终答案从‘事实忠实度’、‘证据支撑度’打分，评分持久化回库，形成 Prompt 调优与业务演进的数据飞轮。

# 第四模块：高频工程难题与防灾避坑篇

### Q15: 如果 Agent 陷入递归死循环，如何从物理层面杜绝巨额 API 账单？
- **【考察意图】** 考察成本治理（FinOps）、配额熔断机制与异常防御能力。
- **【高分回答策略】**
  > 系统在 **Model Gateway（模型网关）** 层构建了三道物理熔断闸门：
  > 1. **Max Turns / Max Steps 硬性上限**：每个 Agent 的运行任务单（Run）在初始化时配置最大轮次上限（如 10 轮），循环达到上限强制终止并标记为 `partial`；
  > 2. **Token 与费用预算预检（Budget Gate）**：网关在每次模型调用前，读取该企业租户当月的预算配置，已消耗金额达到阈值时直接抛出 `budget_exceeded` 拒绝调用；
  > 3. **累计快照用量审计（Audit Log）**：Pi 运行时在每个回合结束时提供累计 Token 快照，网关严格做快照对账并落库 `api_audit_log`，防止在网络重试时发生重复计费或计量逃逸。

### Q16: 销售员在前端看板并发拖拽商机时，如何防止脏写覆盖？
- **【考察意图】** 考察前端状态机、数据库并发控制与乐观锁设计。
- **【高分回答策略】**
  > 在商机看板（Pipeline Kanban）中，多个销售员可能同时拖动同一个商机卡片。我们坚决不把‘前端拖动成功’当成‘保存成功’：
  > 1. **乐观锁并发控制**：更新请求必须携带前端读取数据时的 `expected_updated_at` 时间戳；
  > 2. **条件更新 SQL**：后端执行 `UPDATE leads SET stage = :new_stage, updated_at = now() WHERE id = :id AND updated_at = :expected_updated_at`；
  > 3. **冲突处理**：如果受影响行数为 0，说明自读取后已被他人改动，API 立即返回 409 Conflict；
  > 4. **前端回滚与失效重新拉取**：前端 TanStack Query 捕获 409 后，立即让本地卡片回弹到原位置，并触发 query 失效重新拉取最新数据，弹窗提示销售员最新状态。

### Q17: 外部动作审批执行时，若进程在调用后网络记账前崩溃，系统如何防范重复发送？
- **【考察意图】** 考察分布式事务中的不确定性状态处理（In-doubt transactions）与幂等设计。
- **【高分回答策略】**
  > 这是生产中最经典的‘两将军问题’。如果在调用外部 WhatsApp 网关发出消息后、本地数据库尚未落账标记 `executed` 前服务器断电，系统无法证明动作到底执行了没有。
  > 
  > 我们的核心解法是**‘不确定性安全标记（Safety over Green）’**：
  > 1. 系统坚决**不提供盲目的无脑重试按钮**；
  > 2. 崩溃恢复或超时捕获后，调用 `markWorkbenchApprovedActionUncertain`，将动作状态标记为 `effect_may_have_completed`（效果可能已发生）；
  > 3. 运行状态置为 `partial` 并触发人工核对告警。**宁可让内部销售员花 10 秒人工核实一次，也绝对不冒向外部客户重复发送两条营销消息的风险**。在企业级设计中，安全永远高于盲目的状态变绿。

### Q18: 面试中如果被问到“系统在真实生产中的完成度与边界”时，如何专业作答？
- **【考察意图】** 考察技术人员的诚信度、务实态度与对生产就绪（Production-Ready）的清醒认识。
- **【高分回答策略】**
  > 一个优秀的工程师最忌讳吹嘘系统‘100% 完美无瑕’。面对这个问题，展现**严密的工程边界意识**才是最高分的回答：
  > 
  > 我会清晰地向面试官划分三个层面：
  > 1. **已完全跑通并具备生产级保障的链路**：全栈多租户 RLS 隔离体系、前后端 Zod 契约与 Route Handlers；基于 Pi SDK 的 Agent Loop 执行循环与受控工具前置拦截；HITL 审批两阶段事务流转、乐观锁补偿机制与死信队列重试；Mem0 哈希隔离记忆读取与 WeKnora 带版本哈希的 Wiki 知识召回；
  > 2. **设计上刻意受控的安全边界（不是缺陷，而是规范）**：工作台默认不开启无人值守的全自动外发，所有外部副作用强制进待审提案；历史录制与合成演示数据严格与线上真实数据库环境物理分离；
  > 3. **演进中的优化方向**：进一步提升多 Agent 协作时更细粒度的局部任务断点恢复能力；持续扩充微信生态之外的多渠道（如 Telegram / 邮件）连接器。
  > 这种务实、清晰说明‘什么已做成、什么受控防范、边界在哪里’的态度，往往能获得资深架构师面试官的高度认可。
